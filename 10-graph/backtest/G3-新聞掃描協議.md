# G3 新聞掃描協議：把事件選擇權從我手上拿走

建立：2026-08-14 ｜ 上游：[[G2-前瞻登記]]

---

## 為什麼要做這個

[[G2-前瞻登記]] 的弱點那一節寫過一個**沒有堵住**的漏洞：

> **我可能會選擇性地建節點**——只在覺得有把握時才建。
> 資格條件是客觀的，但「要不要建」仍是主觀決定。

固定排程掃描 + **全記錄**，把「要不要建」從主觀決定變成機械執行。
**這不是自動化的便利，是方法論的修補。**

---

## 執行規格

**頻率：** 每週一次
**寫入方式：** 符合資格者**直接凍結，事後告知**
——一旦需要人確認，選擇權就又回來了

### 資格條件（四條全中才處理）

1. **可定日期**——能指到具體某一天
2. **落在現有領域**——戰爭／政治／能源／糧食／AI／市場／媒體
3. **引擎可達 ≥ 3 個 outcome 節點**（用 `--snapshot` 實測，不是估計）
4. **結果未知**——所有目標時間層的結果都還沒實現

### 全記錄規則（**這條才是真正堵洞的機制**）

> **每次掃描都必須記錄所有候選事件，包含被判定不合格的，以及淘汰理由。**

光有客觀條件不夠——邊緣案例還是可以偏心。
**淘汰清單本身就是審計軌跡**：事後可以檢查我是不是系統性地淘汰某類事件。

沒有候選也要寫「本週無」。**空白的紀錄跟有內容的紀錄一樣重要。**

### 新聞來源的耦合問題（已知，已緩解）

這個 vault 的主題**就是媒體結構**，用新聞選事件等於讓被研究的對象決定樣本。

**緩解：只從新聞取「什麼時候發生了什麼」，不取任何因果解釋或影響評估。**
後者必須來自圖。新聞提供的是事件與日期，不是分析。

這不能完全消除偏誤（媒體決定什麼算「重大事件」），但把耦合限制在
**事件選擇**這一層，不讓它污染**傳導推論**。

## 無 vault 執行

排程每次是全新的雲端 session，**裝置橋接不保證在**——使用者電腦沒開就一定沒有。
所以：

| 元件 | 位置 | 用途 |
|---|---|---|
| `graph_snapshot.json` | Project | 整張圖的攜帶格式（76 節點）|
| `propagate.py` | Project | 引擎本體 |
| 掃描紀錄與凍結預測 | Project | 帶時間戳，跨 session 持久 |

執行：`python3 propagate.py <事件> --snapshot graph_snapshot.json`

**快照要在圖有變動時重新匯出**（`engine/export_snapshot.py`），
否則排程用的是舊圖。⚠️ 這是一個會漂移的地方，尚未自動化。

---

## 每次掃描的產出

寫進 Project 的 `claude/G3-掃描-YYYY-MM-DD.md`：

1. 掃描區間與涵蓋範圍
2. **所有候選事件**與逐條資格判定（含淘汰理由）
3. 符合資格者：節點定義、引擎完整輸出、**凍結時間戳**
4. 到期日登記（依各時間層）

## 計分

沿用 [[G2-前瞻登記]] 的規則，不另立：

- 只計 `type: outcome` 且 |淨信心| ≥ 0.10
- **未覆蓋計為錯誤**，不是棄權
- **至少 3 個獨立事件、15 筆判斷才做第一次整體評估**

---

## 這個協議自己還沒解決的

1. **快照會過期。** 圖改了但沒重新匯出，排程就用舊圖跑。未自動化。
2. **「重大事件」的定義仍有彈性。** 資格條件約束了處理與否，
   但「哪些事件進入候選名單」還是由掃描時的判斷決定。
   全記錄讓這一層可被審計，但沒有消除它。
3. **回饋極慢。** 中期判斷要 1–3 年才知道對錯。
   這個協議在 2027 年之前不會產出任何準確率。
4. **世界只跑一次。** 見 [[G2-前瞻登記]] D 段——樣本永遠很小，
   這是根本限制不是設計缺陷。
