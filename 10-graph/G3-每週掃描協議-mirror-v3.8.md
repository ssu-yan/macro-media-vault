## 圖的真實來源是 seed 腳本，不是 `nodes/*.md`（v3.1 新增）

**這一節放在最前面，因為 2026-08-20 已經有人（Lucas）因為不知道這件事而給錯做法。**

vault 的 `10-graph/` 結構：

```
10-graph/
  engine/
    graphlib.py          ← 節點產生器（格式定義，各 seed 共用）
    seed_ruua.py         ← 俄烏子圖    ▲
    seed_ai.py           ← AI 子圖      │ 這四支（＋日後新增的）
    seed_uschina.py      ← 美中子圖    │ 才是圖的單一真實來源
    seed_chokepoint.py   ← 航道子圖    ▼（2026-08-21 落地）
    export_snapshot.py   ← 讀 ../nodes/*.md → graph_snapshot.json
    propagate.py         ← 傳導引擎
  nodes/
    *.md                 ← **產生出來的成品，不可手改**
```

**每個 `nodes/*.md` 的檔尾都印著「本檔由 `engine/seed_*.py` 產生，請勿直接編輯」。**

**手改 `.md` 會在下次重跑該 seed 腳本時被無聲覆蓋。** 沒有警告、沒有衝突、沒有備份。

所以：

- **要改既有節點或既有的邊** → 改對應的 `seed_*.py`，重跑它
- **要新增一組節點** → 新增一支 `seed_<主題>.py`（用 `from graphlib import Graph`），重跑它
- **`export_snapshot.py` 讀的是 `nodes/`**，所以順序一定是：改 seed → 跑 seed → 跑 export

> `graphlib.Graph.write()` **只覆蓋自己產生的那些檔案**，不會清空 `nodes/` 目錄。
> 所以手寫的 `.md` 不會立刻消失——它會安靜地活著，直到某天那個 id 剛好被某支 seed 產生為止。
> **這種延遲的、無聲的失效比立刻報錯危險得多。**

> **vault 的實體位置（v3.7 明訂）**：`C:\Users\Wendy\macro-media-vault`。
> **2026-09-02 已移出 OneDrive**，舊路徑 `C:\Users\Wendy\OneDrive\macro-media-vault`
> 只剩一個空殼。另一個 vault（生活與規劃）在 `C:\Users\Wendy\wendy-vault`。
> **雲端排程 session 讀不到任何一個**（見〈已知未解的問題〉第 7 條），
> 這兩個路徑只對本機執行者有意義。

## 每次執行的步驟

### 1. 取得工具並驗證完整性

從本 Project 讀取並寫到工作目錄：

- `claude/graph-engine.py` → 存成 `propagate.py`
- `claude/graph-snapshot.json` → 存成 `graph_snapshot.json`

需要 `pyyaml`（`pip install pyyaml --break-system-packages`）。

**⚠️ 取得方式本身有風險，必須檢查。** `project_read` 以 inline 文字回傳整份檔案，
執行者要把 85 KB、140 條邊的 JSON **逐字謄寫**一份到工作目錄。
**謄錯一個 `confidence` 不會有任何警告，而且會直接改變凍結的判斷。**

四道檢查（(d) 為 v3.1 新增）：

```bash
# (a) 引擎跑得動、節點數對
python3 propagate.py --list --snapshot graph_snapshot.json | grep "圖中共"
#     → 應顯示「圖中共 84 個節點」
#       84 = 快照的 81 + 載入器為跨層目標自動補的 3 個 external 佔位節點
#       (S3-信念離散度上升、S4-敘事加速、L4-集中化vs碎片化)
#       **這 3 個不是快照多出節點。看到 84 是正常的。**
#     用 grep 不要用 head：head 讀到就關管，會讓 Python 噴 BrokenPipeError
#     traceback，看起來像引擎壞了，其實只是管線被提前關閉。

# (b) 結構檢查
python3 - <<'PY'
import json
d=json.load(open('graph_snapshot.json')); n=d['nodes']
e=[(x['id'],y) for x in n for y in x.get('edges',[])]
assert d['node_count']==len(n)==81, ('節點數不符', d['node_count'], len(n))
assert len({x['id'] for x in n})==81, 'id 有重複'
assert len(e)==140, ('邊數不符', len(e))
assert all(0<y['confidence']<=1 for _,y in e), 'confidence 值域錯誤'
assert all(y['sign'] in (1,-1) for _,y in e), 'sign 非 ±1'
assert all(y['lag_months'][0]<=y['lag_months'][1] for _,y in e), 'lag_months 顛倒'
print('結構檢查通過：81 節點 / 140 邊')
PY

# (d) 引擎版本（v3.1 新增）
grep -n 'ENGINE_VERSION' propagate.py
#     → 應為 ENGINE_VERSION = "1.1"
#     若 grep 沒有任何輸出，那是 v1.0——**停下來，不要用它產生任何凍結登記**，見下。
```

**(c) 逐位元比對。** 結構對不代表內容對——謄寫可能改掉某條邊的 confidence 而節點數與邊數不變。
派一個**獨立子代理**重新從 Project 取回這兩份檔案、寫到另一個目錄、做 `sha256sum` 與
`json.load(a)==json.load(b)` 比對，只回報結論不回報內容。
用子代理是刻意的：**同一份記憶自我驗證等於沒驗證。**

> **已知的良性差異（兩類，v3.2 補第二類）**：
>
> 1. **檔尾換行**：`project_write` 上傳時會吃掉檔尾換行，
>    所以 Project 版本可能比本地版本少一個位元組。
> 2. **CRLF vs LF**：**快照若由 Windows 上的 `export_snapshot.py` 產生，
>    行尾是 CRLF**；Linux／雲端產生的是 LF。2026-08-21 實測：同一份圖，
>    Windows 版 87,320 bytes（2,879 個 CRLF）、Linux 版 84,441 bytes，
>    **正規化換行後位元組完全相同**。目前 Project 上的快照是 Windows 產生的 CRLF 版。
>
> **判準一律以 `json.load(a) == json.load(b)` 為準。**
> 上述兩類差異不算不符；除此之外的任何位元組差異都要停下來。

> 第三次之所以被抓到，是因為那週的候選剛好被寫成提案而在提案階段回查了原文。
> **如果那週沒有寫提案，錯誤會一直留在紀錄裡，並在日後被引用。那是運氣，不是機制。**
>
> 共同的失敗模式：**數字看起來很具體，所以被當成已查證。**

**統計資料發布不是事件。** CPI、PPI、GDP、就業、消費者信心這類資料，
是**日後核對凍結判斷的對照值**，不是傳導輸入。
判準：`type: outcome` 的節點沒有出邊，不能當入口。
這類候選仍要寫進紀錄並標 `R5`——擋掉的動作本身要留痕。

### 3. 逐條判定資格

四條全中才登記：

1. **可定日期**——能指到具體某一天
2. **落在現有領域**——戰爭／政治／能源／糧食／AI／市場／媒體
3. **事件改變圖的狀態**（v3 重寫，見下）
4. **結果未知**——所有目標時間層的結果都還沒實現

#### 條件 3（v3 重寫）：事件必須改變圖的狀態

**舊版（v1/v2）：「引擎實測可達 ≥ 3 個 outcome 節點」。這條寫錯了。**
它問的是「圖裡有沒有路徑」，而**任何一個既有節點都自動滿足**——
全圖 6 個 `event` 型節點在預設參數下全部通過。
它完全沒有問「這個事件有沒有改變任何東西」。

**新版：事件必須落在下列三類之一，並依該類處置。**

| 類 | 情形 | 處置 |
|---|---|---|
| **3-A** | 圖裡沒有能表達這個事件的入口，需要**新建節點** | **本週不登記**，標 `R7`，列入第 8 節的補圖清單 |
| **3-B** | 事件使某個**既有節點的參數需要調整**（狀態、邊的信心、時滯、或新增／刪除某條邊） | **本週不登記**，標 `R7`，寫出「哪個節點的哪個參數、從什麼改成什麼、機制上的理由」，列入補圖清單 |
| **3-C** | 事件只是既有節點所述機制的**又一次實例**，不需要新節點也不改變任何參數 | **不合格**，標 `R8 不改變圖的狀態` |

**沒有第四類。掃描本身不產生登記。**
登記只在第 8 節的補圖流程走完、Wendy 核可、圖實際更動之後才發生。

**為什麼要這麼嚴：** 2026-08-14 的四筆登記全部落在 3-C
（多邊制裁加碼 → `ST-SANCTIONS`、無人機關稅 → `EV-TARIFF-ESCALATION`、
Nvidia 融資平台 → `EV-AI-CAPEX-CYCLE`、烏克蘭出口下修 → `ST-UA-FARMLAND`），
四段凍結輸出**沒有一段包含本週事件的任何資訊**。
下週若又有一輪關稅，用同一個入口會得到**逐字相同**的輸出。
**同一份預測登記兩次，不是兩個樣本；而且 2027 年真的觀察到 TTF 上漲時，
無法區分那是 2026-08-07 的制裁造成的還是 2022 年那批。不可證偽的登記不是登記。**

#### 可達性仍然要測，但降級為輔助檢查

補圖或調參之後、正式登記之前，仍要實測入口可達的 outcome 節點數。
**≥ 3 才登記**，否則這筆登記可計分的判斷太少、沒有檢驗價值。

口徑寫死（不得事後調整）：

- 只算 `type: outcome`，**`external` 型節點不算**
- 算**不重複的節點數**，不是時間層判斷筆數
- **不套用 |淨信心| ≥ 0.10 那條門檻**——那是計分規則，不是入場規則
- 參數寫死：`--depth 5 --min-conf 0.05`

指令寫死：

```bash
python3 propagate.py <節點 id> --snapshot graph_snapshot.json --depth 5 --min-conf 0.05
```

**入口一律用節點 id，不得用標籤或別名。**
`出口管制` 同時是 `EV-CHIP-CONTROL-TIGHTEN`（下游 10 個 outcome）與
`ST-EXPORT-CONTROL`（4 個）的別名；`關鍵礦物` 同時屬於 `OUT-RARE-EARTH`（0 個）與
`ST-CHINA-RETALIATE`（11 個）。引擎遇到完全比對撞名會**取字典順序第一個、
exit code 0、不出任何警告**。用別名等於把入口交給檔案裡的先後順序決定。

### 4. 全記錄（**這條才是真正堵洞的機制**）

> **必須記錄所有候選事件，包含被判定不合格的，以及淘汰理由。**

客觀條件擋不住邊緣案例偏心；**淘汰清單本身就是審計軌跡**，
事後可以檢查是不是系統性地淘汰某類事件。

**沒有任何候選也要寫「本週無」並說明掃了什麼。**
空白紀錄跟有內容的紀錄一樣重要。

**v3 起，這一節是每週掃描的主產物。**

#### 淘汰理由用固定代碼

| 代碼 | 意義 |
|---|---|
| `R1` | 無法定日期／僅為意向表態 |
| `R2` | 領域外 |
| `R3a` | 圖中無合適入口節點（併入 `R7`，保留代碼供舊紀錄對照） |
| `R3b` | 有入口但可達 outcome < 3 |
| `R4` | 結果已實現 |
| `R5` | 屬結果觀測（統計資料發布），非輸入事件 |
| `R6` | 方向無法表達（見下） |
| `R7` | **待補圖／待調參**——需要新節點或參數變更，已列入補圖清單（v3 新增） |
| `R8` | **不改變圖的狀態**——既有機制的又一次實例（v3 新增） |

**每週紀錄要附一張代碼統計表。** 目的就是讓「系統性淘汰某類事件」一眼看得出來。

#### 補記已凍結紀錄的漏失（v3.2 新增）

事後發現前週漏掉某事件（或某事件的某個面向）時：

- **不得修改已寫入的舊掃描紀錄。** 修改凍結紀錄來掩蓋問題比問題本身嚴重。
- 在**本週**紀錄開一段〈前週補記〉，寫明：漏掉什麼、原本記成什麼、
  何時、因何發現、以及它會不會改變當時的判定。
- 若補記的內容會改變當時的淘汰代碼，**在本週的代碼統計表外另計**，不回頭改舊表。

#### `R6` 方向無法表達——一個已知的系統性偏誤

圖裡的事件節點都是「情況變壞」的語意：`EV-TARIFF-ESCALATION` 是關稅**升級**、
`EV-CHIP-CONTROL-TIGHTEN` 是管制**收緊**。遇到相反方向的事件
（貿易自由化、制裁鬆綁、管制放寬、停火），**引擎沒有把事件 sign 反過來輸入的功能**。

**所以要明說：本協議目前只能登記「情況變壞」方向的事件。**
標 `R6` 而不是混進 `R7`，就是為了讓它可被統計。

### 5. 凍結（僅適用於已完成第 8 節流程的登記）

跑完整引擎輸出，**原封不動**貼進紀錄，加上凍結時間戳。
不得事後修改。不得只貼「重點」。

同時記錄：引擎版本（報表標頭會印）、**輸出的 sha256**、使用的完整指令、
**以及第 8 節的參數變更紀錄與其時間戳**。
**（v3.8）以及天真基準欄**——每個要計分的 outcome 各一列，
算法見〈計分規則〉的〈天真基準〉一節。**基準與引擎輸出同時凍結，不得事後補填。**

**為什麼要 sha256**：凍結的意義在於**事後可以重跑來稽核有沒有被動過**。
引擎 v1.0 的輸出**不可重現**——`report()` 用集合迭代，字串雜湊每個行程隨機化。
v1.1 已改為排序輸出，五次連跑逐字相同。

> **對舊紀錄的處置**：2026-08-14 之前凍結的輸出是 v1.0 產生的，
> 在 v1.1 下不會逐字重現（標頭多一行版本、反向力量段落順序不同）。
> **這是預期內的，不是紀錄被動過。** 計分用的「可觀察結果」段落在兩版之間逐字相同，
> 已用全圖 76 個節點的 JSON 輸出逐一比對驗證（76/76 完全相同）。
> **舊紀錄不需要重做，也不得重做——包括已被判定無效的那四筆。**

#### 登記前的重複檢查（v3 新增）

登記前必須比對**所有**既有登記。
**若入口節點相同，或 outcome 節點重疊超過一半，判定為重複，不計入樣本。**
重複仍要記錄，理由寫「與 YYYY-MM-DD 的登記 X 重複」。

**同一入口節點一週只登記一次。**

   ⚠️ **理由只能援引事件的機制，不得援引預期的結果方向。**

#### 怎麼改圖（v3.1 新增，具體做法）

| 要做的事 | 怎麼做 |
|---|---|
| 改既有節點的參數或既有的邊 | 改對應的 `seed_*.py`，重跑該支 |
| 為既有節點加一條新邊 | 改該節點所屬的 `seed_*.py`（在它的 edges list 加一個 7-tuple） |
| 新增一組主題節點 | 新增 `seed_<主題>.py`，`from graphlib import Graph` |
| **手改 `nodes/*.md`** | **禁止。** 會在下次重跑該 seed 時被無聲覆蓋 |

邊的 7-tuple 欄位順序（見 `graphlib.py`）：
`(to, sign, [lag_min, lag_max], confidence, mechanism, evidence, breaks_if)`

⚠️ `graphlib` 產生 YAML 時，`mechanism`／`evidence`／`breaks_if` 是用雙引號包起來的
（`'    mechanism: "%s"'`）。**這三個欄位的內容裡不能出現半形雙引號**，否則產生的
frontmatter 會壞掉，而且 `export_snapshot.py` 只會靜靜跳過那個節點（`yaml.safe_load` 失敗
→ `continue`），**節點數會少一個而沒有任何錯誤訊息**。

1. 重跑改動到的每一支 `seed_*.py`，再跑 `export_snapshot.py`，

   **Git 不會備份它。**（**v3.7 更正**：v3.4 曾把「Project 那份是唯一的跨機器副本」
   改成「不精確——vault 在 OneDrive 底下，OneDrive 也在同步這個檔」。
   **2026-09-02 vault 已移出 OneDrive，那個第二份副本沒有了。**
   所以原句**回復為正確**：`graph_snapshot.json` 進不了 Git、也沒有雲端同步，

## 計分規則（現在寫死，不得事後調整）

- 只計 `type: outcome` 且 |淨信心| ≥ 0.10 的判斷
- 對照基準＝事件發生前一個月；比較該時間窗的**平均水準**
- **未覆蓋（引擎沒傳導到）計為錯誤，不是棄權**

### 天真基準（v3.8 新增，2026-09-03 Wendy 核可）

**每筆登記在凍結時，除了引擎的判斷，必須同時記錄一個天真基準的判斷。**

基準的算法寫死（不得事後調整）：

> 對每一個要計分的 outcome，基準的預測方向 ＝
> **該指標在事件日之前 12 個月的漂移方向**——
> 即（事件前一個月的平均水準）−（事件前 13 個月的平均水準），取正負號。
> 若該差距的絕對值小於該指標同期 12 個月標準差的 **0.25 倍**，記為「方向不明」
> （與引擎的 |淨信心| < 0.10 對齊，讓兩邊的棄權門檻可比）。

計分時，**引擎與基準用完全相同的規則各算一次錯誤率，兩個數字並列**。

**為什麼要有它**：沒有對照組的準確率不是準確率。
下面那張錯誤率判定表的三個門檻（≤25%／25–50%／>50%）是**對著空氣訂的**——
若三筆登記湊滿後圖的錯誤率是 30%，而天真基準也是 30%，
那張圖沒有提供任何超出「延續過去一年趨勢」的東西；
若基準是 55%，那 30% 才有意義。**在有基準之前，任何錯誤率都無法解讀。**

⚠️ **這是「事前補上比較設計」，不是「事後調整計分口徑」。**
計分規則寫死不得事後調整——**那條規定要防的是「看到結果之後改變評分方式」**。
本次修訂發生在 2026-09-03，而最早的到期日是 **2026-11-17**，
**目前沒有任何一筆判斷被計分過**，所以此時加基準不涉及任何已知結果。
**過了 2026-11-17 之後就不得再加或再改** —— 那時候加就是事後了。

⚠️ **基準欄必須在凍結時就填好**，與引擎輸出同時凍結、一起記進 sha256 的範圍。
**事後補填的基準等於沒有基準**——事後才算，就可以挑一個讓圖好看的算法。

⚠️ **既有的第 1 筆登記（2026-08-25）沒有基準欄。**
它凍結於 v3.8 之前，**不得回頭補**（那會變成事後補填，且違反不改凍結紀錄）。
處置：**該筆在計分時單獨列出並註明「無基準」**，
它的錯誤率只能當敘述性資訊，不得單獨用來判定圖有沒有前瞻價值。
**基準比較從第 2 筆登記起適用。**
